## 2. 产品定位

### 2.1 一句话定位

**帮助招投标从业者自动发现投标文件与招标文件之间的响应偏离、缺失、参数不一致，降低人工核对成本，提升中标材料质量。**

### 2.2 核心价值主张

| 痛点 | 传统做法 | 本产品价值 |
|---|---|---|
| 招标文件需求分散在 Word 各章节、表格、编号段落中 | 人工逐条摘录，易遗漏 | 自动分区、分类、提取为结构化需求条目 |
| 投标文件页数多（几百上千页），人工逐条核对效率低 | 依赖经验和关键词搜索 | 语义匹配 + 规则检查，自动标出偏离位置 |
| 同一类产品投多个项目，需求复用困难 | 每份需求重新整理 | 项目化 Repository，需求可沉淀、可确认、可复用 |
| 技术参数、服务期限、资质证书等关键项易出错 | 肉眼比对，出错率高 | 针对数值/时间/证书/证明材料的专项检测 |
| 截图、资质证书图片内容难以核验 | 人工翻阅附件 | OCR 识别截图文字并与需求关键词/证书库比对 |
| 校对结果难以导出和跟踪 | 手工记录 Excel | 自动生成 Excel 校对清单和带标注的 Word 副本 |

### 2.3 产品形态

- **桌面端工具**：基于 Streamlit 的本地应用，适合个人/小团队在无服务器环境下使用。
- **核心文件格式**：Microsoft Word（.docx / .doc）。
- **数据处理**：本地运行，敏感招投标文件不上传云端。

## 3. 目标用户与用户画像

### 3.1 主要用户

| 角色 | 职责 | 使用场景 | 核心诉求 |
|---|---|---|---|
| **投标专员/商务人员** | 准备投标文件、响应招标要求 | 上传招标文件和投标文件，查看校对结果，补充响应 | 快速定位漏答、错答，降低废标风险 |
| **售前/解决方案工程师** | 编写技术方案、参数响应 | 核对技术指标、服务期限、资质证书是否满足 | 确保技术参数不偏离、证明材料齐全 |
| **项目经理** | 审核投标文件质量 | 批量校对多份投标，导出清单 | 一眼看清所有风险点和遗漏项 |
| **法务/合规人员** | 审核商务条款、格式要求 | 检查必须响应项、签字盖章、格式封装 | 不漏掉强制性和格式类要求 |

### 3.2 用户画像示例

**小王，投标专员，28 岁**
- 每周要投 2-3 个项目，每份招标文件 100-300 页，投标文件 200-800 页。
- 习惯用 Word 写标书，用 Excel 做需求响应矩阵。
- 最头疼的事：招标文件里技术指标分散在正文、表格、评分标准里，投标时容易漏响应或参数写错。
- 期望：上传两个 Word，系统自动告诉我哪里没响应、哪里参数不对、哪里缺少证书截图。

## 4. 核心使用场景

### 4.1 场景一：单项目快速校对（已有功能）

1. 用户上传 1 份招标文件 + 1 份投标文件。
2. 系统自动提取招标需求条目。
3. 系统将需求与投标段落做语义匹配。
4. 输出带标注的 Word（首页问题总览 + 正文标红批注）、Excel 校对清单、偏离表、证明材料索引表。
5. 用户查看带标注 Word，确认问题并在原文中修改。

### 4.2 场景二：批量项目校对（已有功能）

1. 用户上传 1 份或多份招标文件 + 多份投标文件。
2. 系统合并所有招标文件的需求。
3. 对每份投标文件分别执行校对。
4. 生成批量校对总览和单文件详情。

### 4.3 场景三：需求沉淀与复用（重构重点）

1. 用户创建项目（如“某市政府数据中台项目”）。
2. 上传招标文件到项目。
3. 系统自动提取需求条目并展示在需求管理页面。
4. 用户逐条确认、修改、删除、标记 `confirmed`。
5. 后续同一类项目可直接导入/复用已确认需求库。
6. 投标时只需上传投标文件，系统基于确认后的需求执行校对。

### 4.4 场景四：资质与证书一致性核验

1. 招标文件要求提供 ISO9001、等保测评报告、公安部检测报告等。
2. 投标文件中的资质章节或截图里声称已提供。
3. 系统通过 OCR 识别截图文字，检查是否包含要求的证书名称。
4. 若未找到或参数不一致，生成警告。

### 4.5 场景五：技术参数偏离检测

1. 招标要求“系统可用性不低于 99.9%”。
2. 投标写“系统可用性 99.5%”。
3. 系统识别数值、单位和比较方向，判定为参数偏离。
4. 标红提示并给出修改建议。

## 6. 关键实体与数据模型（产品视角）

### 6.1 项目（Project）

- 项目是需求管理和校对的基本单位。
- 一个项目对应一次招标/投标活动。
- 项目下包含：招标文件源文件、解析后的需求条目、已上传的投标文件（可选）。

### 6.2 需求条目（RequirementItem）

从产品经理视角，需求条目是系统的“最小可校对单元”。每个条目应包含：

| 属性 | 产品含义 |
|---|---|
| ID | 条目唯一标识，便于在报告中引用 |
| stable_hash | 语义去重用的稳定哈希，同一需求在不同提取中保持一致 |
| 来源文档 | 来自哪份招标文件 |
| 章节路径 | 条目在招标文件中的位置，帮助用户回溯 |
| 原始文本 | 招标文件原文 |
| 分类 | 技术参数 / 商务条款 / 资质条件 / 评分标准 / 交付要求 / ... |
| 约束类型 | 必须 / 评分项 / 建议 / 仅供参考 |
| 检查方式 | 规则检查 / LLM 检查 / 人工确认 |
| 复核状态（review_status） | 草稿（draft）/ 已确认（confirmed）/ 已修改（modified）/ 已拒绝（rejected） |
| 是否需证明材料 | 是否要求提供证书/报告/截图 |

### 6.3 偏离问题（Issue）

校对结果以“问题”为单位呈现：

| 问题类型 | 含义 |
|---|---|
| 缺失响应 | 投标文件中未找到对应需求的内容 |
| 参数不一致 | 数值/单位/方向与需求不符 |
| 时间/期限不一致 | 服务期限、交付期、质保期等不符 |
| 关键词缺失 | 需求中的关键实体/证书/资质未出现 |
| 疑似未响应 | 语义匹配度低，可能未实质回应 |

## 7. 用户旅程（User Journey）

### 7.1 新建项目并沉淀需求

```
打开系统
  → 创建新项目（输入项目 ID、项目名称）
  → 进入「需求管理」页面
  → 上传招标文件（可多个）
  → 点击「自动提取需求」
  → 系统展示提取出的需求列表
  → 用户逐条检查、编辑、删除、确认
  → 点击「全部确认」保存到项目
```

**关键体验点**：
- 提取结果需要展示来源章节，便于用户判断提取是否准确。
- 对于表格提取的条目，应显示表头信息，避免只看单元格内容失去上下文。
- 用户编辑后需保留版本信息，支持追溯。

### 7.2 基于项目校对投标文件

```
进入已有项目
  → 确认项目中已有「已确认」需求
  → 上传投标文件
  → 点击「开始校对」
  → 系统加载确认需求并执行校对
  → 展示校对结果总览
  → 查看偏离分析、文档对照、候选匹配
  → 导出 Excel 校对清单 / 带标注 Word（首页问题总览 + 正文标红批注）/ 偏离表 / 证明材料索引表
```

**关键体验点**：
- 只使用 `review_status=confirmed` 的已确认需求，避免草稿/错误条目干扰校对。
- 多份投标文件批量校对时，需求只需加载一次。
- 校对失败（如文件损坏、OCR 模型缺失）应单独展示，不中断其他文件。

### 7.3 传统快速校对（不创建项目）

```
在「文档校对」页面
  → 上传招标文件
  → 上传投标文件
  → 点击「开始校对」
  → 直接查看结果并导出
```

**适用场景**：临时性、一次性校对，不需要沉淀需求。

## 9. 关键设计原则

### 9.1 准确性优先

- 校对系统的生命线是**少漏报、少误报**。
- 对“必须响应项”宁可误报也不漏报；对“评分项”允许一定程度的灵活匹配。
- 数值/时间/资质类检查优先用规则，语义类检查可逐步引入 LLM。

### 9.2 可解释性

- 每个问题都要能定位到：**需求条目、投标原文位置、判断依据**。
- 提供“候选匹配”让用户看到系统为什么选了这段响应。
- 标注版 Word 直接标红问题片段，降低理解成本。

### 9.3 人机协同

- 系统自动提取需求后，必须允许人工确认/修改。
- 需求管理页面是产品核心，不是可选项。
- 用户对确认后的需求有最终控制权。

### 9.4 数据安全

- 招投标文件通常含敏感商业信息。
- 当前设计为本地运行，不依赖外部 API（除非主动开启 LLM）。
- OCR 模型本地加载，图片识别不上传云端。

### 9.5 可扩展性

- 提取器、检查器、匹配器都基于接口设计，方便新增类型。
- Repository 抽象允许未来替换为 SQLite/数据库实现。
- 需求分类、约束类型、检查方法均使用枚举，便于扩展。

## 10. 交互与界面设计要点

### 10.1 导航结构

```
侧边栏
  ├─ 文档校对（已有）
  └─ 需求管理（新增）
```

### 10.2 需求管理页面

- **顶部**：项目选择/创建、操作类型（选择现有 / 创建新）。
- **中部**：文件上传区（支持多文件）。
- **操作区**：「自动提取需求」按钮。
- **表格区**：
  - 列：ID、原始文本、分类、约束类型、检查方式、复核状态、来源文档、章节路径。
  - 可编辑：分类、约束类型、复核状态、原始文本。
  - 禁用编辑：ID、stable_hash、创建时间、修改时间、版本。
- **底部**：「保存修改」、「全部确认」按钮。

### 10.3 校对结果页面

- **总览卡片**：成功/失败文件数、问题数量分布（致命/高/中/低）。
- **文件选择器**：批量校对时切换查看不同投标文件。
- **Tab 页**：
  - 文档对照：左右分栏展示需求原文与投标原文。
  - 偏离分析：问题卡片，左右原文对照，候选匹配。
  - 报价核对：报价表三处金额对照，差异单元格标红。
  - 商务信息核对：项目/投标人名称、保证金、授权书等商务风险项。
- **导出按钮**：Excel 清单、**带标注 Word（首页问题总览 + 正文标红批注）**、偏离表、证明材料索引表。

### 10.4 异常处理

- 文件格式不支持：提示用户仅支持 .docx / .doc。
- OCR 模型未安装：提示用户关闭 OCR 或安装依赖。
- 某份投标文件解析失败：记录到失败列表，继续处理其他文件。

### 10.5 偏离表与证明材料索引导出

偏离表和证明材料索引表定位为**评标专用附件**，不是用户修改投标文件的主界面。用户修改投标文件的主界面是**带标注 Word**。

两类表格均由系统填充「需求—响应—材料位置」及问题标记，**不需要用户手工填写说明**。

**偏离表导出结构：**

| 条款号 | 需求原文 | 投标响应原文 | 偏离情况 | 证明材料位置 | 问题标记 |
|---|---|---|---|---|---|
| 3.2.1 | 系统可用性 ≥ 99.9% | 系统可用性 99.95% | 正偏离 | P12 | |
| 4.1.3 | 质保期 3 年 | 质保期 2 年 | 负偏离 | P8 | 低于要求 |
| 5.2 | 提供 ISO9001 证书 | 已提供 ISO9001 证书 | 无偏离 | P45 附件 3 | |

- **条款号/需求原文**：来自已确认的 `RequirementItem`。
- **投标响应原文**：来自语义匹配命中的投标段落；未命中时留空并标记「未响应」。
- **偏离情况**：系统根据参数/关键词/时间检查自动判定为「无偏离」「正偏离」「负偏离」或「未响应」。
- **证明材料位置**：系统给出投标文件中匹配段落的页码或章节路径；涉及截图/证书时，给出附件页码。
- **问题标记**：系统对异常项给出简短标记，如「低于要求」「未响应」「参数不符」等。

Issue 类型到偏离情况的映射：
- 「参数不一致」「时间/期限不一致」→ 根据方向判定为「正偏离」或「负偏离」。
- 「缺失响应」「疑似未响应」「关键词缺失」→ 「未响应」。
- 无问题 → 「无偏离」。

**证明材料索引表导出结构：**

| 评分项/需求项 | 招标文件要求 | 需提供的证明材料 | 实际材料位置 | 是否提供 | 缺失标记 |
|---|---|---|---|---|---|
| 技术部分 2.1 | 提供等保三级报告 | 等保测评报告 | P38 附件 3 | ✅ | |
| 商务部分 1.4 | 近 3 年业绩 ≥ 500 万 | 合同、验收报告 | P22-P28 | ✅ | |
| 资质部分 3.2 | 项目经理具备 PMP 证书 | PMP 证书复印件 | 未找到 | ❌ | 缺材料 |

- **评分项/需求项**：来自 `RequirementItem` 的章节路径或分类。
- **需提供的证明材料**：由系统根据需求分类和关键词推断（如「等保」「ISO」「业绩」）。
- **实际材料位置**：OCR 识别或文本匹配找到的页码/附件位置；未找到时显示「未找到」。
- **缺失标记**：系统自动标红缺材料项。

导出格式默认为 Excel，同时支持 Word 表格形式，方便直接贴入投标文件。

### 10.6 带标注 Word 输出格式

带标注 Word 是用户修改投标文件的主输出，结构如下：

**首页：校对报告总览**

| 项目 | 内容 |
|---|---|
| 校对文件 | XXX 项目投标文件.docx |
| 招标文件 | XXX 项目招标文件.docx |
| 校对时间 | 2026-08-17 |
| 问题统计 | 致命 X 项 / 高 X 项 / 中 X 项 / 低 X 项 |

首页问题清单（示例）：

| 序号 | 类型 | 需求/条款 | 投标原文位置 | 问题描述 | 建议 |

| 1 | 参数偏离 | 质保期 ≥ 3 年 | P12 表格第 3 行 | 投标写 2 年 | 改为 ≥ 3 年 |

- 问题位置用红色高亮或下划线标出。

## 12. 风险与应对

### 12.1 技术风险

| 风险 | 影响 | 应对 |

| 风险 | 影响 | 应对 |

| 风险 | 影响 | 应对 |

## 15. 需要重点关注的产品细节

### 15.1 需求提取的边界

- 不是所有段落都是需求。标题、说明性文字、页眉页脚应被过滤。
- 表格中的“符合/是/否”列通常是响应列，不应被当成需求内容。
- 评分标准表格中的每一行应作为独立评分项提取。

### 15.2 需求分类的产品含义

| 分类 | 校对重点 |
|---|---|
| 技术参数 | 数值、单位、方向（≥/≤） |
| 商务条款 | 付款方式、质保期、交付期 |
| 资质条件 | 证书、报告、资质、人员资格 |
| 评分标准 | 分值、证明材料、响应格式 |
| 交付要求 | 交付物、交付时间、实施地点、验收条件 |
| 项目标识信息 | 项目名称、项目编号、投标人名称 |
| 封装格式 | 签字盖章、页码、装订要求 |

### 15.3 复核状态的工作流

- **草稿（draft）**：系统自动提取，未经过人工确认。
- **已确认（confirmed）**：人工确认无误，可用于校对。
- **已修改（modified）**：人工修改过，需重新确认。
- **已拒绝（rejected）**：不是有效需求，不参与校对。

产品应保证：只有 `review_status=confirmed` 的需求才会进入校对流程。

### 15.4 投标拆分的业务逻辑

- 投标文件通常包含商务、技术、价格、资质等部分。
- 拆分后应保留每个段落的章节上下文，便于匹配时排除不相关部分。
- 产品名称/章节标题可用于把需求精确归到对应产品（多产品投标场景）。

### 15.5 OCR 检查的触发条件

- 仅当需求涉及“证明材料/证书/截图”时才重点检查图片。
- 避免对所有图片都做 OCR，减少误报和性能开销。
- 图片上下文段落应与需求章节/产品一致，避免 A 产品的证书要求误判到 B 产品截图。

### 15.6 报价校验的产品细节

报价一致性错误是投标文件中最常见的废标风险之一，需作为独立检查器（`quote_checker`）实现，不混入通用 `consistency_checker`。

**需识别的报价表格类型：**

1. **投标函/报价函**：通常包含投标总价、大写金额、投标有效期、工期。
2. **报价一览表**：汇总各分项总价。
3. **分项报价表**：明细到每一项的单价、数量、合价、税率、税费。

**校验规则：**

| 规则 | 说明 | 严重级别 |
|---|---|---|
| 总价一致性 | 投标函总价 = 报价一览表合计 = Σ 分项报价表合价 | 致命（废标风险） |
| 大小写金额一致 | 小写金额与大写金额数值相同 | 致命 |
| 单价 × 数量 = 合价 | 分项报价表中每行算术校验 | 致命 |
| 税费计算 | 合价 = 不含税价 + 税额；税额 = 不含税价 × 税率 | 高 |
| 币种/单位统一 | 全部使用人民币、万元/元一致 | 高 |
| 低于成本价提醒 | 明显低于预算控制价或行业均值时提示用户准备说明 | 中 |

**产品交互：**

- 报价校验结果在校对结果页面单独成 Tab「报价核对」。
- 以表格形式展示三处来源的金额，差异单元格标红。
- 对无法识别的报价表格，提示用户手动框选区域。
- 大写金额解析支持常见中文数字写法（壹贰叁、一二三等）。

### 15.7 商务信息校验的产品细节

除报价外，投标文件中还有四类高频废标风险项需要专项校验：项目标识信息、投标人信息、投标保证金、法定代表人授权书。

**15.7.1 项目标识信息一致性（`bidder_info` 的一部分）**

- **校验对象**：项目名称、项目编号。
- **校验规则**：
  - 招标文件封面、正文、页眉页脚中的项目名/编号应一致。
  - 投标文件封面、投标函、页眉页脚中的项目名/编号应与招标文件一致。
- **输出**：在带标注 Word 首页列出「项目标识信息不一致」项，标红差异位置。

**15.7.2 投标人名称一致性（`bidder_info` 的另一部分）**

- **校验对象**：投标人公司名称、联合体成员名称及牵头人。
- **校验规则**：
  - 投标文件封面、投标函中的投标人名称应与营业执照、资质证书中的名称一致。
  - 联合体投标时，校验联合体协议中列明的所有成员名称及牵头人是否在其他材料中一致出现。
- **输出**：不一致项标红，首页列出「投标人名称不一致」风险提示。

**15.7.3 投标保证金校验（`bid_bond`）**

- **校验对象**：投标保证金金额、缴纳方式、到账凭证。
- **校验规则**：
  - 保证金金额 = 招标文件要求金额。
  - 缴纳方式符合要求（电汇/保函/保险）。
  - 保证金缴纳凭证（电汇回单/保函扫描件）在投标文件中存在。
  - 到账时间应在投标截止时间之前（如凭证中有日期信息）。
- **输出**：在「商务信息核对」Tab 中展示保证金要求 vs 实际响应；缺失凭证标红。

**15.7.4 法定代表人授权书校验（`authorization`）**

- **校验对象**：法定代表人授权书、被授权人信息、签字人一致性。
- **校验规则**：
  - 授权书在投标文件中存在。
  - 授权期限覆盖投标有效期。
  - 被授权人信息与投标函/联系人信息一致。
  - 签字人与授权书中被授权人姓名一致（如 OCR 可识别）。
- **输出**：缺失授权书或有效期不足时作为致命错误标红；签字人不一致时作为高风险警告。

### 15.8 扩展校验能力（中优先级，不着急实现）

以下校验项对提升覆盖度有价值，但实现依赖更稳定的 OCR/表格解析，计划在 Phase 2 逐步补充。

**15.8.1 营业执照深度校验**

- 校验营业执照在有效期内。
- 校验经营范围覆盖投标内容关键词。
- 将营业执照纳入证书库管理。

**15.8.2 业绩证明深度校验**

- 从合同/验收证明中提取：合同金额、签订时间、项目内容、甲方名称。
- 与招标文件要求的业绩门槛（如近 3 年、金额 ≥ 500 万）比对。
- 在证明材料索引表中展示关键信息是否满足要求。

**15.8.3 财务状况校验**

- 识别审计报告中的出具年份、会计师事务所名称。
- 提取资产负债率、净利润等关键指标（如表格可读）。
- 与招标文件财务门槛比对。

**15.8.4 纳税与社保证明校验**

- 识别纳税证明、社保缴纳证明中的缴纳期间。
- 校验是否覆盖招标文件要求的近 3/6 个月。
- 对不连续或缺失月份给出提示。

**15.8.5 项目团队人员校验**

- 识别人员简历、资格证书、社保缴纳证明。
- 校验人员资质是否满足岗位要求。
- 检测同一人是否在多个岗位重复任职。

**15.8.6 目录页码一致性校验**

- 提取目录中的章节标题与页码。
- 与正文实际页码比对，标记断页、跳页、目录条目缺失。

**15.8.7 联合体协议校验**

- 当招标文件允许/要求联合体时，检测联合体协议是否存在。
- 校验协议中的成员名称、分工、牵头人是否与其他材料一致。
- 非联合体投标时忽略。

**15.8.8 招标文件澄清版本管理**

- 在 Repository 中增加「澄清/答疑文件」类型。
- 支持上传多份澄清文件并记录版本。
- 当澄清文件修改已确认需求时，自动标记该需求为「已修改」状态，提醒用户重新确认。

### 15.9 真实文档回归后的新增产品细节

基于对 6 份真实招投标文件的回归分析（详见 `2026-08-20-real-tender-gap-analysis-design.md`），产品需要额外关注以下设计点：

**15.9.1 文档类型与采购方式识别**

- 招标文件存在「比选文件」「竞争性磋商文件」「招标文件」「遴选文件」等形态；投标文件存在「报名文件」「响应文件」「产品解决方案」等形态。
- 系统应在解析阶段识别文档类型，并据此加载不同的期望结构与校验规则集。
- 对「报名文件」不应要求存在完整的技术/价格部分；对「响应文件」则应校验资格/商务/技术/价格四段式结构。
- 识别采用三层策略：规则 → embedding 相似度 → 本地 LLM；输出必须包含 `confidence`。
  - `confidence ≥ 0.85`：直接采用。
  - `0.70 ≤ confidence < 0.85`：UI 预填推荐类型，用户可一键确认或修改。
  - `confidence < 0.70`：UI 强制要求用户选择文档类型。

**15.9.2 评分表作为独立需求来源**

- 评分表常位于「响应供应商须知」或「评审」章节，与用户需求书分离。
- 评分表中的每一行应作为 `RequirementItem` 提取，约束类型为 `SCORING`，并记录分值与评分细则。
- 对无法拆分为单条的聚合评分规则（如「全部响应得 24 分，每负偏离一项扣 3 分」），保留为 `EvaluationRule`，Phase 3/LLM 再与具体需求条目关联。
- `★` 标记映射为 `MANDATORY`，`▲` 标记映射为 `SCORING`，保留原始标记便于展示。

**15.9.3 响应表/偏离表优先匹配**

- 投标方常在「技术响应偏离表」「商务条款响应表」中集中应答。
- 系统应识别这些表格，把「响应内容/偏离情况」列作为对应需求的首选匹配文本，而不是仅匹配正文段落。

**15.9.4 证明材料的类型化校验**

- 资格截图不是单一类型，而是包含信用中国 4 类查询、中国政府采购网、广东政府采购智慧云平台、全国认证认可信息公共服务平台等。
- 证书类材料需校验有效期、认证范围、证书主体。
- 业绩合同需校验签订时间是否在近三年范围内、金额是否与业绩表一致、是否包含双方盖章页。

**15.9.5 跨文档一致性扩展**

- 除了项目名称/编号、投标人名称，还需校验：投标有效期、合同履行期限/服务期限、付款方式、交付地点、授权代表一致性、授权有效期覆盖性。
- 这些校验应集中在 `cross_document_checker` 中统一输出，避免散落在多个检查器里。

**15.9.6 新增模块与既有 Pipeline 的接口衔接**

- 新增 checker 不直接修改 `semantic_matcher` 的输出结构，统一输出 `Issue` 列表，由 `Proofreader.pipeline` 汇总后交给 exporters。
- OCR 类 checker（screenshot/certificate/personnel/performance）共享 `EmbeddedImage` + OCR 结果，避免重复识别同一张图片。
- 每个 checker 需声明自身可识别的 `IssueType` 与置信度，低置信度 Issue 在 UI 中显示为「需人工复核」而非「错误」。
- 具体接口契约、输入输出、Issue 类型映射、OCR/LLM 准确率评估详见 `2026-08-20-real-tender-gap-analysis-design.md` 第 8.4、8.5、8.6 节。

**15.9.7 无法识别即提示复核，不静默跳过**

- 所有 checker 遵循统一原则：当无法识别证据或无法做出可靠判断时，必须生成 `UNRECOGNIZED_EVIDENCE` 类型的 Issue，不允许直接 `return []` 静默跳过。
- 严重级别按需求约束类型区分：强制项（`★`）为高/致命，评分项（`▲`）为中，普通建议项为低。
- UI 中以「需人工复核」标签聚合展示，避免弹窗轰炸。

**15.9.8 统一的日期/期间归一化模块**

- 新增 `date_normalizer` 工具模块，统一解析证书有效期、合同签订日期、社保缴纳期间、投标有效期、服务期限等时间表达。
- 支持绝对日期、日期范围、相对期间（近三年、近 6 个月、90 天内）以及中文数字日期。
- 无法解析时返回 `None` 并触发「需人工复核」提示。

## 16. 待决策事项

1. **是否强制要求用户先创建项目再校对？**
   - 建议：不强制。保留「文档校对」快速入口，「需求管理」作为增强工作流。

2. **需求管理页面中，用户编辑后是否立即保存？**
   - 建议：采用显式「保存修改」按钮，避免误操作。

3. **`load_parsed` 是否在本次重构中实现？**
   - 建议：Phase 1 保持 stub，Task 12 中表格检查用空 `ParsedDocument` 或重新解析兜底。

4. **是否允许删除系统自动提取的需求条目？**
   - 建议：允许删除，但保留操作日志或版本信息。

5. **OCR 默认开启还是默认关闭？**
   - 建议：默认开启，但首次启动明确提示加载时间和可关闭选项。

6. **OCR 低置信度结果如何处理？**
   - 建议：低于阈值（如 0.70-0.80）的识别结果不直接生成致命/高 Issue，而是标记为「需人工复核」；具体阈值按能力类型区分，详见 `2026-08-20-real-tender-gap-analysis-design.md` 第 8.5 节。

7. **LLM 是否默认启用？**
   - 建议：默认关闭。仅在本地模型或用户明确配置的安全环境下可选开启，且输出必须带有「模型判断」标签，提醒用户重点复核。

## 17. 总结

「智能投标文件校对系统」的核心产品价值在于：**把招标文件中分散、非结构化的需求转化为可管理、可校对的条目，并通过语义匹配和规则检查自动发现投标响应中的偏离**。当前重构阶段的重点是把需求提取链路产品化（Repository + 需求管理页面），同时解决新版数据模型与下游模块的接口不一致问题。

产品成功的关键在于：**自动提取要准、人工确认要轻、校对结果要可信、导出报告要能用**。后续实现应始终围绕这四个目标展开。
