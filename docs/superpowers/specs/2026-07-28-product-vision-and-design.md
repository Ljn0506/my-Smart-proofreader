## 2. 产品定位

### 2.1 一句话定位

**帮助招投标从业者自动发现投标文件与招标文件之间的响应偏离、缺失、参数不一致和格式问题，降低人工核对成本，提升中标材料质量。**

### 2.2 核心价值主张

| 痛点 | 传统做法 | 本产品价值 |
|---|---|---|
| 招标文件需求分散在 Word 各章节、表格、编号段落中 | 人工逐条摘录，易遗漏 | 自动分区、分类、提取为结构化需求条目 |
| 投标文件页数多（几百上千页），人工逐条核对效率低 | 依赖经验和关键词搜索 | 语义匹配 + 规则检查，自动标出偏离位置 |
| 同一类产品投多个项目，需求复用困难 | 每份需求重新整理 | 项目化 Repository，需求可沉淀、可确认、可复用 |
| 技术参数、服务期限、资质证书等关键项易出错 | 肉眼比对，出错率高 | 针对数值/时间/证书/证明材料的专项检测 |
| 截图、资质证书图片内容难以核验 | 人工翻阅附件 | OCR 识别截图文字并与需求关键词/证书库比对 |
| 校对结果难以导出和跟踪 | 手工记录 Excel | 自动生成 Excel 校对清单和带标注的 Word 副本 |

### 2.3 产品形态

- **桌面端工具**：基于 Streamlit 的本地应用，适合个人/小团队在无服务器环境下使用。
- **核心文件格式**：Microsoft Word（.docx / .doc）。
- **数据处理**：本地运行，敏感招投标文件不上传云端。

## 3. 目标用户与用户画像

### 3.1 主要用户

| 角色 | 职责 | 使用场景 | 核心诉求 |
|---|---|---|---|
| **投标专员/商务人员** | 准备投标文件、响应招标要求 | 上传招标文件和投标文件，查看校对结果，补充响应 | 快速定位漏答、错答，降低废标风险 |
| **售前/解决方案工程师** | 编写技术方案、参数响应 | 核对技术指标、服务期限、资质证书是否满足 | 确保技术参数不偏离、证明材料齐全 |
| **项目经理** | 审核投标文件质量 | 批量校对多份投标，导出清单 | 一眼看清所有风险点和遗漏项 |
| **法务/合规人员** | 审核商务条款、格式要求 | 检查必须响应项、签字盖章、格式封装 | 不漏掉强制性和格式类要求 |

### 3.2 用户画像示例

**小王，投标专员，28 岁**
- 每周要投 2-3 个项目，每份招标文件 100-300 页，投标文件 200-800 页。
- 习惯用 Word 写标书，用 Excel 做需求响应矩阵。
- 最头疼的事：招标文件里技术指标分散在正文、表格、评分标准里，投标时容易漏响应或参数写错。
- 期望：上传两个 Word，系统自动告诉我哪里没响应、哪里参数不对、哪里缺少证书截图。

## 4. 核心使用场景

### 4.1 场景一：单项目快速校对（已有功能）

1. 用户上传 1 份招标文件 + 1 份投标文件。
2. 系统自动提取招标需求条目。
3. 系统将需求与投标段落做语义匹配。
4. 输出偏离分析、错别字、截图 OCR、表格比对结果。
5. 用户查看并导出 Excel 报告和标注版 Word。

### 4.2 场景二：批量项目校对（已有功能）

1. 用户上传 1 份或多份招标文件 + 多份投标文件。
2. 系统合并所有招标文件的需求。
3. 对每份投标文件分别执行校对。
4. 生成批量校对总览和单文件详情。

### 4.3 场景三：需求沉淀与复用（重构重点）

1. 用户创建项目（如“某市政府数据中台项目”）。
2. 上传招标文件到项目。
3. 系统自动提取需求条目并展示在需求管理页面。
4. 用户逐条确认、修改、删除、标记 `confirmed`。
5. 后续同一类项目可直接导入/复用已确认需求库。
6. 投标时只需上传投标文件，系统基于确认后的需求执行校对。

### 4.4 场景四：资质与证书一致性核验

1. 招标文件要求提供 ISO9001、等保测评报告、公安部检测报告等。
2. 投标文件中的资质章节或截图里声称已提供。
3. 系统通过 OCR 识别截图文字，检查是否包含要求的证书名称。
4. 若未找到或参数不一致，生成警告。

### 4.5 场景五：技术参数偏离检测

1. 招标要求“系统可用性不低于 99.9%”。
2. 投标写“系统可用性 99.5%”。
3. 系统识别数值、单位和比较方向，判定为参数偏离。
4. 标红提示并给出修改建议。

## 6. 关键实体与数据模型（产品视角）

### 6.1 项目（Project）

- 项目是需求管理和校对的基本单位。
- 一个项目对应一次招标/投标活动。
- 项目下包含：招标文件源文件、解析后的需求条目、已上传的投标文件（可选）。

### 6.2 需求条目（RequirementItem）

从产品经理视角，需求条目是系统的“最小可校对单元”。每个条目应包含：

| 属性 | 产品含义 |
|---|---|
| ID | 条目唯一标识，便于在报告中引用 |
| 来源文档 | 来自哪份招标文件 |
| 章节路径 | 条目在招标文件中的位置，帮助用户回溯 |
| 原始文本 | 招标文件原文 |
| 分类 | 技术参数 / 商务条款 / 资质条件 / 评分标准 / 交付要求 / ... |
| 约束类型 | 必须 / 评分项 / 建议 / 仅供参考 |
| 检查方式 | 规则检查 / LLM 检查 / 人工确认 |
| 复核状态 | 草稿 / 已确认 / 已修改 / 已拒绝 |
| 证明材料 | 是否要求提供证书/报告/截图 |

### 6.3 偏离问题（Issue）

校对结果以“问题”为单位呈现：

| 问题类型 | 含义 |
|---|---|
| 缺失响应 | 投标文件中未找到对应需求的内容 |
| 参数不一致 | 数值/单位/方向与需求不符 |
| 时间/期限不一致 | 服务期限、交付期、质保期等不符 |
| 关键词缺失 | 需求中的关键实体/证书/资质未出现 |
| 疑似未响应 | 语义匹配度低，可能未实质回应 |

## 7. 用户旅程（User Journey）

### 7.1 新建项目并沉淀需求

```
打开系统
  → 创建新项目（输入项目 ID、项目名称）
  → 进入「需求管理」页面
  → 上传招标文件（可多个）
  → 点击「自动提取需求」
  → 系统展示提取出的需求列表
  → 用户逐条检查、编辑、删除、确认
  → 点击「全部确认」保存到项目
```

**关键体验点**：
- 提取结果需要展示来源章节，便于用户判断提取是否准确。
- 对于表格提取的条目，应显示表头信息，避免只看单元格内容失去上下文。
- 用户编辑后需保留版本信息，支持追溯。

### 7.2 基于项目校对投标文件

```
进入已有项目
  → 确认项目中已有「已确认」需求
  → 上传投标文件
  → 点击「开始校对」
  → 系统加载确认需求并执行校对
  → 展示校对结果总览
  → 查看偏离分析、文档对照、候选匹配
  → 导出 Excel 校对清单 / 带标注 Word
```

**关键体验点**：
- 只使用 `review_status=CONFIRMED` 的需求，避免草稿/错误条目干扰校对。
- 多份投标文件批量校对时，需求只需加载一次。
- 校对失败（如文件损坏、OCR 模型缺失）应单独展示，不中断其他文件。

### 7.3 传统快速校对（不创建项目）

```
在「文档校对」页面
  → 上传招标文件
  → 上传投标文件
  → 点击「开始校对」
  → 直接查看结果并导出
```

**适用场景**：临时性、一次性校对，不需要沉淀需求。

## 9. 关键设计原则

### 9.1 准确性优先

- 校对系统的生命线是**少漏报、少误报**。
- 对“必须响应项”宁可误报也不漏报；对“评分项”允许一定程度的灵活匹配。
- 数值/时间/资质类检查优先用规则，语义类检查可逐步引入 LLM。

### 9.2 可解释性

- 每个问题都要能定位到：**需求条目、投标原文位置、判断依据**。
- 提供“候选匹配”让用户看到系统为什么选了这段响应。
- 标注版 Word 直接标红问题片段，降低理解成本。

### 9.3 人机协同

- 系统自动提取需求后，必须允许人工确认/修改。
- 需求管理页面是产品核心，不是可选项。
- 用户对确认后的需求有最终控制权。

### 9.4 数据安全

- 招投标文件通常含敏感商业信息。
- 当前设计为本地运行，不依赖外部 API（除非主动开启 LLM）。
- OCR 模型本地加载，图片识别不上传云端。

### 9.5 可扩展性

- 提取器、检查器、匹配器都基于接口设计，方便新增类型。
- Repository 抽象允许未来替换为 SQLite/数据库实现。
- 需求分类、约束类型、检查方法均使用枚举，便于扩展。

## 10. 交互与界面设计要点

### 10.1 导航结构

```
侧边栏
  ├─ 文档校对（已有）
  └─ 需求管理（新增）
```

### 10.2 需求管理页面

- **顶部**：项目选择/创建、操作类型（选择现有 / 创建新）。
- **中部**：文件上传区（支持多文件）。
- **操作区**：「自动提取需求」按钮。
- **表格区**：
  - 列：ID、原始文本、分类、约束类型、检查方式、复核状态、来源文档、章节路径。
  - 可编辑：分类、约束类型、复核状态、原始文本。
  - 禁用编辑：ID、stable_hash、创建时间、修改时间、版本。
- **底部**：「保存修改」、「全部确认」按钮。

### 10.3 校对结果页面

- **总览卡片**：成功/失败文件数、问题数量分布。
- **文件选择器**：批量校对时切换查看不同投标文件。
- **Tab 页**：
  - 文档对照：左右分栏展示需求原文与投标原文。
  - 偏离分析：问题卡片，左右原文对照，候选匹配。
- **导出按钮**：Excel 清单、带标注 Word。

### 10.4 异常处理

- 文件格式不支持：提示用户仅支持 .docx / .doc。
- OCR 模型未安装：提示用户关闭 OCR 或安装依赖。
- 某份投标文件解析失败：记录到失败列表，继续处理其他文件。

## 11. 成功指标（KPI）

### 11.1 技术指标

| 指标 | 目标 | 说明 |
|---|---|---|
| 需求提取召回率 | ≥ 90% | 招标文件中真正构成需求的条目被提取出来的比例 |
| 需求提取准确率 | ≥ 85% | 提取出的条目中确实是需求（非标题、非噪声）的比例 |
| 语义匹配 Top-1 命中率 | ≥ 80% | 投标响应被正确匹配到需求的比例 |
| 参数偏离误报率 | ≤ 15% | 被判定为参数偏离但实际无偏离的比例 |
| 缺失响应漏报率 | ≤ 5% | 实际未响应但系统未检测出的比例 |

### 11.2 业务指标

| 指标 | 目标 | 说明 |
|---|---|---|
| 单份标书校对时间 | 从小时级降到分钟级 | 200 页投标文件在 5 分钟内完成 |
| 人工复核效率 | 提升 50% 以上 | 通过结构化条目和标注定位减少翻阅时间 |
| 废标风险项遗漏率 | 显著降低 |  especially 强制性资质/证书/参数 |

### 11.3 用户指标

- 需求管理页面中用户确认/修改的条目比例（反映自动提取可信度）。
- 导出报告的使用频率。
- 批量校对功能的使用频率（反映产品对工作流的融入度）。

## 12. 风险与应对

### 12.1 技术风险

| 风险 | 影响 | 应对 |
|---|---|---|
| Word 格式多样，解析不稳定 | 需求提取失败或错位 | 持续积累真实样本，完善段落类型和表格分类规则 |
| 语义匹配误报/漏报 | 用户不信任结果 | 提供候选匹配、可调整阈值；关键项优先用规则 |
| OCR 模型大、加载慢 | 首次使用体验差 | 默认启用但可关闭；缓存 Reader 实例；提示加载进度 |
| 大文件性能差 | 校对时间过长 | 支持分批处理、进度条；必要时限制单次上传文件数 |

### 12.2 产品风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 用户不习惯先管理需求再校对 | 新流程 adoption 低 | 保留传统快速校对入口；需求管理作为增强功能 |
| 自动提取结果不准确导致用户不愿确认 | 需求库质量差 | 优化提取器；提供便捷的编辑和批量确认 |
| 多项目需求复用场景不清晰 | 功能闲置 | 先聚焦“单次项目沉淀”，再逐步做跨项目导入 |

### 12.3 合规风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 使用 LLM 可能泄露敏感内容 | 用户数据外传 | 默认关闭 LLM；所有模型本地加载 |
| 自动校对结果导致投标失误 | 法律责任 | 产品明确标注“校对结果仅供参考，最终由人工复核” |

## 13. 竞品/替代方案对标

| 方案 | 优点 | 缺点 | 本产品差异 |
|---|---|---|---|
| 人工 Excel 响应矩阵 | 灵活、可控 | 耗时、易漏、难维护 | 自动化提取 + 语义匹配 |
| 通用文档比对工具 | 速度快 | 不懂招投标语义 | 针对需求-响应场景专项优化 |
| 招投标 SaaS 平台 | 功能全 | 需上传文件、费用高、数据外泄风险 | 本地运行、低成本、可定制 |

## 15. 需要重点关注的产品细节

### 15.1 需求提取的边界

- 不是所有段落都是需求。标题、说明性文字、页眉页脚应被过滤。
- 表格中的“符合/是/否”列通常是响应列，不应被当成需求内容。
- 评分标准表格中的每一行应作为独立评分项提取。

### 15.2 需求分类的产品含义

| 分类 | 校对重点 |
|---|---|
| 技术参数 | 数值、单位、方向（≥/≤） |
| 商务条款 | 付款方式、质保期、交付期 |
| 资质条件 | 证书、报告、资质、人员资格 |
| 评分标准 | 分值、证明材料、响应格式 |
| 封装格式 | 签字盖章、页码、装订要求 |

### 15.3 复核状态的工作流

- **draft**：系统自动提取，未经过人工确认。
- **confirmed**：人工确认无误，可用于校对。
- **modified**：人工修改过，需重新确认。
- **rejected**：不是有效需求，不参与校对。

产品应保证：只有 `confirmed` 的需求才会进入校对流程。

### 15.4 投标拆分的业务逻辑

- 投标文件通常包含商务、技术、价格、资质等部分。
- 拆分后应保留每个段落的章节上下文，便于匹配时排除不相关部分。
- 产品名称/章节标题可用于把需求精确归到对应产品（多产品投标场景）。

### 15.5 OCR 检查的触发条件

- 仅当需求涉及“证明材料/证书/截图”时才重点检查图片。
- 避免对所有图片都做 OCR，减少误报和性能开销。
- 图片上下文段落应与需求章节/产品一致，避免 A 产品的证书要求误判到 B 产品截图。

## 17. 总结

「智能投标文件校对系统」的核心产品价值在于：**把招标文件中分散、非结构化的需求转化为可管理、可校对的条目，并通过语义匹配和规则检查自动发现投标响应中的偏离**。当前重构阶段的重点是把需求提取链路产品化（Repository + 需求管理页面），同时解决新版数据模型与下游模块的接口不一致问题。

产品成功的关键在于：**自动提取要准、人工确认要轻、校对结果要可信、导出报告要能用**。后续实现应始终围绕这四个目标展开。
